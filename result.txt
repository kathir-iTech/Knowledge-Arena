# KNOWLEDGE ARENA — COMPLETE ARCHITECTURAL ASSESSMENT

---

## 1. ARCHITECTURE UNDERSTANDING

```
Browser (React 19 / Next.js 15 App Router)
  ├─ Client Components (useState, useEffect, useMemo)
  ├─ Server Components (minimal - mostly client-driven)
  ├─ Server Actions (AI PDF Forge only)
  └─ API Routes (REST: admin, executive, commander, gladiator, messaging, AI)
       │
       ├── Firebase Web SDK (client-side: Auth, Firestore realtime)
       ├── Firebase Admin SDK (server-side: API routes, AI engines)
       └── Genkit + Gemini (AI PDF Forge, Knowledge, Prediction, Decision Support)
            └── pdfreader (PDF extraction)
```

**Key characteristics:**
- **Monolithic Next.js deployment** — single codebase, no microservices
- **Client-heavy architecture** — most business logic runs in browser components
- **Direct Firestore access from client** — services call Firestore Web SDK directly
- **Dual role naming** — DB stores `teacher`/`student`, AuthContext maps to `commander`/`gladiator`
- **No shared service layer** — server routes reimplement logic from scratch with Admin SDK
- **No state management library** — everything is `useState` in React context
- **No test infrastructure** — zero tests exist
- **In-memory rate limiting** — not suitable for multi-instance production

## 19. SCALABILITY REVIEW

### Current Bottlenecks
1. **Ad-hoc analytics** — Every executive workspace load queries ALL quizzes + participants + submissions (15-20 Firestore reads per request, grows linearly with data)
2. **In-memory rate limiter** — Lost on restart, not shared across instances
3. **No pagination on workspace API** — `limit(2000)` on quizzes snapshot
4. **Client-side subscriptions** — Every battle participant maintains a Firestore `onSnapshot` listener
5. **Single-instance Server Actions** — PDF generation blocks the Node.js event loop during extraction + AI call
6. **No Firestore usage optimization** — No caching, no denormalized counts, no aggregation documents

### Scalability Thresholds
- **Users**: ~500 before analytics queries become noticeably slow (ad-hoc computation O(n) on all entities)
- **Concurrent battles**: ~50 before client-side subscription volume affects Firestore costs
- **PDF generation**: ~10 concurrent before Server Action execution queue saturates

### Recommendations
1. Pre-compute analytics on write (Firestore triggers or scheduled functions)
2. Distributed rate limiting (Firestore-based)
3. Paginate workspace API responses
4. Reduce subscription scope — only subscribe to needed fields
5. Offload PDF extraction to background job (Cloud Tasks or similar)
6. Add aggregation documents (`arena_stats/global`, `arena_stats/daily`)

### Verdict
The repository has a **solid foundation** with comprehensive API surfaces, good Firestore security rules, and a working core battle flow. However, it has **significant structural debt** (dual role naming, client-driven game logic, monolithic components, zero tests) and **major feature gaps** (pause/resume/skip, replay, AI scheduler, question bank, analytics pipeline).

The product vision demands three well-separated pillars (FORGE, BATTLE, COMMAND). The current codebase has no such separation — everything is mixed into a single Next.js app. A **minimum 2-month refactoring effort** is required to align with the vision before production deployment.

**Next action:** Phase 0 — fix the known bugs and concrete errors identified above, then proceed with the structured refactoring plan.
